Le workflow de release, à chaque changement
===========================================

Deux sortes de tags :
  - tags précis (v2.0.1, v2.0.2, …) : annotés, ne bougent JAMAIS une fois publiés.
  - tag majeur flottant (v2) : force-déplacé sur le dernier tag précis, pour que
    `uses: php-kirigami/kiribuild@v2` suive la dernière v2.x.

# 1. Commit tes changements normalement
git add .
git commit -m "Résumé du changement"
git push origin main

# 2. Crée le tag précis pour cette version
git tag -a v2.0.1 -m "Ce qui a changé"
git push origin v2.0.1

# 3. Déplace le tag flottant majeur pour qu'il pointe dessus
git tag -f v2 v2.0.1
git push origin v2 --force

Le -f (force) à l'étape 3 est normal et attendu — c'est le SEUL tag qu'on déplace.


Première release v2
===================

v2 change l'API : le checkout et le commit sortent de l'action, les inputs `lfs`
et `commit-message` disparaissent. C'est une rupture -> nouveau tag majeur.

git add .
git commit -m "v2: action réduite à node/cli/export"
git push origin main

git tag -a v2.0.0 -m "v2: composite action trimmed to node/cli/export"
git push origin v2.0.0

git tag v2 v2.0.0
git push origin v2

Le tag v1 (et les v1.0.x) reste en place pour les workflows pas encore migrés.
